# 理念

从理论 -> 实践本身，也应当维护好文档主线。也就是要利用 docwarden 开发 docwarden，
和 https://github.com/openai/symphony 的实践一致

在定义实践前，首先应该完善本项目的 ai infra

在这里定义一些要点：

## 当前实现形态

当前 monorepo 同时承载三层：

```text
docwarden = 文档维护 workflow
contexta = context / prompt / capability infrastructure
isomorph = semantic primitive engine
```

`docwarden` 负责 task / review / promote / pick / spec / guide / wiki。

`contexta` 负责 skills、agents、prompts、context files、catalog、install、sync 和 activation。

`isomorph` 负责 concept、assertion、relation、recognition、locator 和 semantic-lint。

codex plugin（skills 族）和 CLI 仍是目标形态，但现在需要先把三层分清楚：

- workflow 由 docwarden 承接。
- prompt / capability 分发由 contexta 承接。
- 语义同构检查由 isomorph 承接。

此前将 semantic-lint 方向放在 contexta 下推进，导致 contexta 名字被底层 semantic engine 占用。当前已将这部分改名为 isomorph。

## self-loop 迭代

所有的 ai 基础建设都应该能够自迭代。

1. skills 需要不断迭代才会变得更好，需要重设计官方的 skill-creator，以更严格的规范和约束设计 skills
2. 需要有 improve skill 的 skill，显示进入优化 skills 的 workflow
3. 需要先让 contexta 管理 docwarden dogfood 所需的 skills / prompts / agents，否则 docwarden workflow 无法获得稳定反馈。

## 文档编写准则

区分原始文档和 ai-generated docs。docs 目录下全部都是人类编写、维护的文档，目前只有作者 sayoriqwq

## 代码与docs link

做 task 的时候不能忘记同步文档更新，需要建立显示追溯机制。无论是在 AGENTS.md 里编写，还是 skill workflow，又或者是脚本。评估这里实现效果的要义是：新 agent 在没有获取任何额外上下文的情况下，能正确的找到 docs，并且按照它的任务更新 docs

## 文档最小化和断言

明确 ai 建立后的文档，需要满足这样的约束：

1. 一份 md 只负责一件事情。单一职责原则
2. md 文档的存储位置（文件夹结构），和命名必须有意义且细致。服务于 agent 搜索
3. 若状态需要持久化存储，且是文件级别，采用 front-matter 形式
4. 接着2,文件夹结构需要有 trace 机制，则需求一个 index.md 文档，唯一作用是指路。告诉来到这的 agent：这个文件夹下的 docs 在做什么，有哪些，怎么找
5. 若文档需要结构化，需要先定义 template，后续创建采用脚本去创建，模型在 template 的基础上修改，绝对不允许模型自由发挥

6. 祈使句提示词的约束：

https://datatracker.ietf.org/doc/html/rfc2119

参见 rfc 规范，learn from https://github.com/openai/symphony

强约束： MUST/MUST NOT

次强约束：SHOULD/SHOULD NOT

模型发挥： MAY

7. md 格式

使用 ofm 约束，尤其是 [[]] 语法定义了文档间的联系和跳转

## skills 组织规范

参考 https://github.com/openai/symphony/tree/main/.codex/skills，这里有着一系列的 skills，一起服务于同一个 workflow

当前 `contexta` 应先解决这一层：

- capability catalog。
- capability install / sync。
- project activation。
- skills / agents / prompts / context files 的分发边界。

它不负责 semantic-lint；semantic-lint 属于 `isomorph`。

## 定位

这是 docwarden 之上的 AI 基建约束，也包含 docwarden 之下的 semantic engine。

当前顺序是：

```text
isomorph 提供 semantic primitive engine
contexta 提供 prompt / capability 基础设施
docwarden 跑文档维护 workflow
```

在开发 docwarden 的同时，需要用 contexta 建立可 dogfood 的 prompt / capability 分发链路，再决定哪些语义稳定性要求下沉到 isomorph。
