# 文档体系理论 v3

> ⚠️ ai warning
>
> 本文承接 v2 之后的 breaking changes。
> 它不覆盖 v2 的历史语境，而是记录 v2 之后已经推进出的新边界。
>
> 2026-05-29 更新：本文记录的是 v3 历史口径。
> 当前口径已被 `理念-v4.md` 取代：`contexta` 回到 context / prompt / capability infrastructure，内容语义 primitive engine 改名为 `isomorph`。

## 一、v3 为什么是 breaking change

v2 的核心修正是把 `working / stable` 拆成：

```text
task -> review system -> spec
                    -> guide
                    -> wiki
```

这个判断仍然成立。

但后续推进表明，仅有 docwarden 的流程层还不够。

文档体系还需要单独维护一套内容语言协议，用来定义 Markdown 内容本身如何被命名、组织、链接、约束和检查。

因此 v3 的 breaking change 是：

```text
docwarden = 操作流程协议
contexta = 内容语言协议
```

这不是在 v2 上补几个字段，而是把原先混在一起的两个系统拆开。

## 二、v2 保留什么

v2 仍然保留以下判断：

- `task` 是短命任务过程层。
- `review system` 负责打开黑盒、降低用户审核成本。
- `spec` 服务 agent 执行。
- `guide` 服务 user 理解。
- `wiki` 服务长期知识网络。
- `docs/` 是 human-maintained source layer。

这些仍属于 docwarden 的操作流程设计。

## 三、v3 改变什么

v3 把 contexta 从“未来要解决的内容格式问题”提升为独立协议。

contexta 不再只是 docwarden 的一个字段设计问题。

它负责维护内容语言，包括：

- `concept`：命名语言。
- `policy`：约束语言。
- `structure`：组织语言。
- `relation`：连接语言。
- `template`：复制骨架。
- `example`：样本语言。
- `semantic-lint`：语义偏移检测语言。

这意味着：

- docwarden 不应直接定义 template、metadata、assertion 或 semantic lint 的内容语义。
- contexta 不应承接 task / review / promote / pick / cleanup 的流程编排。
- 两者可以互相映射，但不能互相吞掉职责。

## 四、当前 contexta 的实体层

contexta 当前已经进入自举阶段。

它通过 `.contexta/mapping/` 表达理论到 Markdown 实体的映射：

```text
.contexta/mapping/
  bootstrap/
    modules/
    relations/
    templates/
    lint/
  docwarden/
    modules/
    templates/
```

含义是：

- `bootstrap` 表达 contexta 如何用自己的内容语言定义自己。
- `docwarden` 表达 contexta 如何为 docwarden 资产提供内容语言。
- `modules` 承载 concept / policy 等 md module。
- `relations` 承载 concept network 的连接表达。
- `templates` 承载复制后的内容骨架。
- `lint` 承载 semantic-lint signal definitions。

因此 `.contexta` 不是 task material。

它是已经 review 过、需要长期稳定读取的 theory 与 practice reference。

## 五、核心理论变化

### module / assertion / composition

当前口径：

- `module` 是 md file scope。
- `assertion` 是 module 内部最小可审查语义判断。
- `assertion` 后续需要能成为 locator target。
- `composition` 是 structure subtype，用来定义 whole / part / stable semantic boundary。

这修正了早期把 assertion 误写成文件、独立资产或完整 locator 机制的倾向。

### kind / metadata

当前口径：

- `kind` 是 content language entry。
- `status / created / updated / owner` 属于 docwarden operation metadata。
- 不能把两类 metadata 压成同一种字段。

这修正了早期把内容类型字段和操作状态字段混在一起的倾向。

### template

当前口径：

- template 只负责复制后的内容骨架。
- template 不负责来源、review、pick、更新、写入或生命周期。
- template 不能反向制造 kind。

这修正了早期把 template 写成 workflow 或 policy 的倾向。

### relation / delimitation

当前口径：

- `relation` 处理 concept network 中的稳定连接。
- `Delimitation` 只处理局部边界压力。
- 不是每个 concept 都需要列满 Concept Relations。

这修正了早期把所有相关概念都塞进 concept module 的倾向。

### structure

当前已验证的 structure subtype 包括：

- `pipeline`：input / transform / output。
- `workflow`：state / move / transition。
- `architecture`：layer / relation / boundary。
- `branch`：condition / route / target。
- `composition`：whole / part / stable semantic boundary。

这些是 structure 的实践参照，不是 `structure_type` metadata 分类树。

### example

当前口径：

- `example` 是样本语言。
- 它用一个具体样本让 agent 学会如何理解、书写或判断某个对象。
- positive / negative / borderline 是写好 example 的教学结构，不是 example 自己的 kind。

这修正了早期把 example 写成 kind、role、template kind 或 directory kind 的倾向。

### semantic lint

当前口径：

- `semantic-lint` 是语义偏移检测语言。
- `signal` 命名 warning。
- `trigger` 表达可观察、可脚本化的触发条件。
- `locator` 指向 module、heading 或未来 assertion。
- 具体 signal definitions 放在独立 lint layer。

当前已经确认的实例化关系是：

```text
raw hit -> candidate -> signal instance
```

完整 CLI lint engine 还没有实现。

当前只保留 signal definitions 和 dry run，作为未来实现的参照物。

## 六、实践与实现的边界

v3 当前阶段不是纯理论，也不是 CLI 实现。

更准确的阶段是：

```text
theory stabilization -> practice reference -> future implementation
```

其中：

- `theory` 负责命名、边界、关系和约束。
- `practice reference` 负责把 theory 落成可读、可链接、可模仿的 Markdown 参照。
- `task material` 负责承接 loop、纠偏、candidate 和 review outcome。
- `implementation` 负责未来 CLI / lint engine / parser 等可执行能力。

implementation 不能反过来私自定义 theory。

如果 CLI 实现暴露理论缺口，应回到 task loop，经 review 后再修改 contexta。

## 七、当前未解决的问题

v3 仍未完成：

- review surface 的详细设计。
- decision trace 的稳定落点。
- spec / guide / wiki 的最小模板。
- contexta format 层。
- assertion locator 的完整机制。
- semantic lint CLI engine。
- lint parser 如何处理 frontmatter、heading、section、code fence、OFM wikilink。
- example quality 如何从真实使用反馈中继续抽象。

## 八、当前结论

v3 的核心不是替换 v2，而是在 v2 的 docwarden 流程模型之外，拆出 contexta 的内容语言模型。

当前最新边界是：

```text
docs/ = human-maintained source layer
.docwarden/task/ = task material
.contexta/mapping/ = theory + practice reference
future CLI = implementation
```

docwarden 继续处理操作流程。

contexta 继续稳定内容语言。

两者通过 mapping 发生关系，但不共享职责。
