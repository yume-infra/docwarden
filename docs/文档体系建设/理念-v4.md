# 文档体系理论 v4

> ⚠️ ai warning
>
> 本文承接 v3 之后的 breaking change。
> v3 保留为历史口径；当前项目以本文为最新分层判断。

## 一、v4 为什么是 breaking change

v3 把 `contexta` 定义为内容语言协议。

后续实现中发现，这一步提前占用了原本更上层的名字。

最初需要的 `contexta` 不是 semantic primitive engine，而是 prompt / context / capability 的基础设施：它应让 agent 能稳定获得项目上下文、skills、agents、prompts 和激活入口。

semantic-lint 方向在推进中意外长成了独立底层能力。它有价值，但不应继续占用 `contexta` 的产品位置。

因此 v4 的 breaking change 是：

```text
docwarden = 文档维护 workflow
contexta = context / prompt / capability infrastructure
isomorph = semantic primitive engine
```

## 二、三层定位

### docwarden

`docwarden` 负责文档维护 workflow。

它回答：

- task 如何承接短期上下文。
- review system 如何打开黑盒。
- promote / pick 如何把 task material 分发到 spec / guide / wiki。
- agent 什么时候能写 `.docwarden`。
- agent 什么时候必须等待 user review。
- `docs/` 何时可以被编辑。

`docwarden` 不直接定义 skill、prompt、agent 或 semantic primitive 的内容语义。

### contexta

`contexta` 负责 context / prompt / capability infrastructure。

它回答：

- 一个项目需要哪些 agent 可消费能力。
- skills、agents、prompts、context files 如何组织。
- capability catalog 如何表达。
- capability 如何 install / sync / activate。
- agent 进入项目时应读取哪些上下文入口。

`contexta` 的核心不是 Markdown semantic lint，也不是文档 workflow。

它的目标是让 workflow 所需的 prompt 和 capability 能被稳定分发、安装和激活。

### isomorph

`isomorph` 负责 semantic primitive engine。

它回答：

- concept / policy / relation / structure / template / example 如何表达。
- module / assertion / locator 如何成立。
- recognition primitive 如何把 Markdown surface 解释成 candidate role。
- semantic-lint 如何从 observable surface 产出 signal。
- theory、Markdown material、runtime result 和未来 exported artifact 之间如何保持语义同构。

`isomorph` 不负责 prompt 分发，不负责 docwarden workflow 编排。

## 三、当前 monorepo 结构

当前 monorepo 同时承载三层：

```text
apps/docwarden/  = docwarden workflow implementation
apps/contexta/   = context / prompt / capability infra implementation
apps/isomorph/   = semantic primitive runtime implementation

.docwarden/      = docwarden task / review / project working material
.isomorph/       = isomorph theory + practice reference material
docs/            = human-maintained source layer
```

当前不使用 `.contexta/` 承载占位配置。

只有当 `contexta` 的 catalog / install / activation 机制真正消费本地配置时，`.contexta/` 才应落地。

## 四、v3 到 v4 的迁移

v3 中的以下内容迁移到 `isomorph`：

- 内容语言协议。
- concept / policy / relation / structure / template / example。
- assertion / locator。
- recognition primitive。
- semantic-lint / signal / trigger。
- `.contexta/mapping/` 中的 theory + practice reference。

当前实现对应为：

```text
apps/contexta/ semantic runtime -> apps/isomorph/
.contexta/mapping/              -> .isomorph/mapping/
```

`contexta` 现在只保留上层 capability infrastructure 的产品位置。

## 五、当前实现状态

当前已完成的实现收口：

- `apps/isomorph` 提供 `isomorph` CLI。
- `isomorph init / recognize / lint / primitive / upgrade / doctor` 承接原 semantic runtime。
- `.isomorph` 成为当前 semantic material 的 origin instance。
- `apps/contexta` 重置为最小 context infra CLI/API 骨架。
- `contexta capability / catalog / install / activation / asset` 只是上层入口，不包含 semantic-lint engine。

当前仍未完成：

- contexta capability catalog 的真实 schema。
- contexta install / sync / activation 的真实写入机制。
- docwarden 需要的第一批 skills / agents / prompts。
- contexta 与 docwarden dogfood 的最小闭环。
- isomorph 是否作为 contexta 的可选底层能力接入。

## 六、边界规则

- `docwarden` MUST NOT 承接 prompt / skill / agent 分发职责。
- `contexta` MUST NOT 重新吸收 semantic primitive engine。
- `isomorph` MUST NOT 承接 task / review / promote / pick workflow。
- `.isomorph` 是 semantic material source。
- `.contexta` 在没有真实消费机制前 MUST NOT 放占位配置。
- `docs/` 仍是 human-maintained source layer；agent 只有在 sayori 明确要求时才能编辑。

## 七、当前结论

v4 的核心是把此前误占的名字还原：

```text
contexta = 给 agent 提供正确上下文与能力的基础设施
isomorph = 保持语义材料在不同形态之间同构的底层引擎
docwarden = 使用这些能力维护文档 workflow 的系统
```

下一步不应继续加深 `isomorph` 的 semantic-lint 能力。

下一步应优先让 `contexta` 提供 docwarden dogfood 所需的最小 capability 分发闭环。
